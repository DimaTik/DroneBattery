# Расчёт напряжения по одному открытому полёту

В журнале PX4 от 28.09.2026 найден участок с малыми скоростями и устойчивой командой тяги. На нём рассчитана медиана напряжения в окне около выбранного момента накопленного висения. Это проверка доступности данных и одного шага будущей обработки батарей.

## Что получилось

Журнал содержит 1051 запись `battery_status`. По принятым настройкам пригоден один участок длительностью 10,40 с. После первых 5,20 с этого участка медиана 20 записей в окне 67,00–70,80 с от начала записи батареи равна **14,40093 В**. При записанной в журнале конфигурации четырёх ячеек это **3,60023 В на ячейку**. Физическая конфигурация батареи отдельно не проверялась.

Для исходного целевого времени 20 с расчёт вернул недостаточность данных: такого времени пригодного висения в этом полёте нет. Чтобы закончить пример расчёта, демонстрационное время уменьшено до 5 с. Этот выбор сделан после просмотра журнала; он не является проверенной настройкой диагностики. Отрицательный результат для 20 с сохранён в `results/target20_insufficient.json`.

Ранее проверен другой публичный журнал, `60f0a65f-fea3-46cc-b8db-23ac20adb24c`: в нём нет `battery_status`, поэтому рассчитать показатель по нему нельзя. Сведения о нём сохранены в `source-rejected.json`; сам этот журнал в комплект не включён.

## Метод и проверки

Временная шкала строится по `battery_status`. Положение, признаки посадки и команда тяги берутся из последней записи не позднее измерения батареи, с ограничением возраста данных. Будущие значения не подставляются. Пропуски разрывают участок. Скорости должны быть валидными, признаки посадки и контакта с землёй отсутствовать. Пороги скоростей, длительности и изменчивости тяги перечислены в `analyze.py` и в результате. Это исследовательские настройки, а не установленные эксплуатационные нормы.

Устойчивость нагрузки приближённо проверяется по норме команды тяги за предыдущие две секунды. Команда тяги не является измерением тока или мощности. Итоговое напряжение не пересчитывается к эталонной нагрузке. Медиана независимо пересчитана стандартной библиотекой из CSV и прямо из исходного ULog. Проверены запрет подстановки будущих данных, отсечение устаревших значений и разрыв участков при пропуске. Результаты в `results/verification.json`.

На графике зелёным выделено пригодное висение, охрой окно расчёта. По всему полёту зарегистрировано 369 событий потери данных. Пример не подтверждает точность диагностики, остаточную ёмкость, ресурс или старение батареи. Нет серии полётов одной батареи и проверенного результата для платформы «Клевер»: исходный аппарат указан как Generic Quadcopter с платой MATEK_H743_SLIM. Температурная компенсация, сопоставление разных батарей и контрольные карты остаются будущей работой.

## Повторение

Python 3.12 или новее. Выполнить из этой папки в отдельном окружении:

```powershell
python -m pip install -r requirements.txt
python analyze.py
python verify.py
```

Отдельный отрицательный опыт:

```powershell
python analyze.py --target-hover-seconds 20 --output results-20
```

Входной файл `flight.ulg`, его адрес, дата получения и SHA-256 записаны в `source.json`. Итог, параметры и время повторного расчёта сохраняются в `results/result.json`; сводная таблица в `results/aligned.csv`, график в `results/calculation.png`. Работу по подготовке примера и расход токенов отдельно не измеряли. Время расчёта измерено от открытия ULog до сохранения графика; при проверенном запуске 1,29 с, на другом компьютере оно изменится.
